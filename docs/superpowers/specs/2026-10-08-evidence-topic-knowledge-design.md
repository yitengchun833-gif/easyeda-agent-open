## 一页流程摘要

**工程师给目标和已有资料 → AI 一次整理必要约束及缺项 → 按需查资料、核对器件 → 展示可审阅方案 → 按功能分批摆件、接线 → 核对真实连接并看图 → 局部修正 → 最终核对、保存 → 按授权进入 PCB → 制造与实物验证 → 值得复用的经验提请审核。**

工程师不维护知识卡，不逐字段填表，不逐根线确认。AI 自动检索并装配证据，只在冲突、影响范围扩大、昂贵或难逆转的选择、正式知识发布时请求判断。已有确认仍有效时直接复用，不为换阶段重复确认。用户已指定设计时，AI 代画并报告疑点，不重新设计。

知识库提供可定位的资料和历史经验；plan.json 是当前目标，snapshot/回执是实际工程。两者不能混成“记忆”。没有参考图，AI 从功能关系与真实引脚组织表达，先给简明方案，再用实际图面检查布局，不强制增加参考图生成步骤。

当前 MOSFET 电源控制工程用作贯穿示例：历史记录为 29 个电路/接口对象、69 个引脚，包含降压、指示、MOSFET 控制和接口。型号、输入范围、负载能力、封装物理映射以已确认资料为准；本设计不从标题、截图或器件额定值推断整机指标。

## C. 五种实际入口与恢复

1. **从零设计**：一次收集当前决定必需的约束→读取资料→提出连接方案；只有影响设计的分歧请求判断。用同一 plan 格式，不新建手册到电路自动生成器。无参考图时 AI 自行组织功能表达并看最终图。
2. **接手已有工程/局部改动**：先查 runtime 摘要和已存基线，按对象/网络读取当前必要信息。布局保持连接；改设计绑定获准新逐脚目标。R2 位号位置调整无需重新解析全部手册。
3. **工程师中途手工修改**：缓存仅作定位；写入前对受影响对象原生读回。发现改动暂停依赖旧坐标/连接的步骤，更新局部观察和方案。若手工改动波及邻网或共享电源才扩大范围，不覆盖用户改动。
4. **断线/超时恢复**：读原动作回执与实际对象，partial/unknown 不整批重放；旧 ID 经重开可能失效，重新绑定。恢复剩余步骤并刷新所需局部证据；最终交付检查针对当前修订，不能沿用断线前截图或 DRC。
5. **缺资料/冲突**：只阻止依赖缺项的决定，其余可独立部分继续准备；列出两个来源和影响，让工程师决定。未确认负载条件时可以代画已确认控制连接，不能承诺电流能力或布线尺寸。

变更影响集合由实际对象/网络、plan 来源和约束引用共同确定。首期由 AI 用已有引用与局部读取装配，不引入全库依赖传播器。局部刷新用于效率，最终范围核对用于交付；不能把增量当成免检。

## D. 五层“正确”分别报告

- 引用可信度：来源版本、定位、完整性、冲突；只证明引用可核对。
- 设计正确性：工程条件、元件适用性、电路推理及工程师确认；不能由 pin-net 一致证明。
- EDA 执行正确性：真实身份、逐脚目标、范围、图面、保存；计划和缓存不是事实。
- 可制造性：封装物理映射、工厂规则/DFM、输出完整性；不能由原理图或单次 DRC 证明。
- 实物性能：实际板、测试条件与测量；没有实测就不标 pass。

## F. 首期端到端切片与实施顺序（尚未批准）

1. **先贯通已有任务文件与知识引用**：只围绕已有 MOSFET/电源模块的一次有证据审查或获准局部变更，AI 自动检索/读所需证据，把可定位引用和条件写入现有 plan 来源/说明，用户看到一份方案，不新增管理界面。所需新的证据字段仅向现有 plan 契约兼容扩展，具体字段实现前核对 schema。
2. **补冻结图文读取**：get 专属图片输出及限制；不能拿当前解析图片冒充历史。文本不足就返回缺项，不自动填造。
3. **完成局部原理图切片**：有证据审查无修改时交付审查结果；获准变更才沿现有 batch 和局部回读执行，最后核对身份/逐脚/图面及任务要求 DRC/保存。首期不清空重画整页，不从零造整板；此为实施后的授权演练，不在本设计轮操作工程。
4. **首期收尾**：输出“当前工程 / 资料内容 / 可判断及未知”，每项判断定位当前对象与证据；若有稳定经验，可用现有 legacy propose 提候选。提交失败不阻止工程审查交付，不谎称已沉淀。
5. **后续再做专题发布增强**：候选 revision、幂等、多结论、审批版本绑定、原子回执/索引 job 与 UI。它们仍按下文设计实施，但不作为首个只读审查切片的依赖。

非首期：完整专题发布 UI 与事务增强、完整 PCB 自动算法、制造全套输出新增适配、自动依赖传播/全库重审、正式知识覆盖、自动规则升级、独立 UI/聊天或第二工作流。PCB 全过程已考虑，但首期不顺带实现。旧 v1 的完整 topic 发布优先级低于证据辅助工程审查：先证明检索能正确服务当前对象，再投入沉淀功能。

局部变更的数据链固定为：**工程任务上下文→相关证据→拟议变更→实际回读差异**。通过当前器件实例及准确型号、脚号/网络、板约束项关联来源。版式修改只读几何和图面规则，通常不查数据手册；器件/连接/工作条件变更才检索对应证据；PCB 改动另读取相关焊盘、路径、机械与制造条件。原理图语义网名可辅助定位但不能代替实例/脚号，资料型号不能直接充当 EDA 对象 ID。计划保留基线/来源哈希，动作绑定 window/target 与受影响 ID，回读记录真正变化及未预期差异。身份、来源或必要条件变化时废止依赖它的旧证据，不重新读取无关模块。

工程版本与证据版本分别绑定：前者是当前快照/观察修订，后者是冻结资料修订。精确料号、封装、订货变体不匹配时禁套近似知识；未知驱动电压、负载和频率保留未知。AI 自动搬运器件/网络编号、claims/evidenceRef/submissionId，用户不填写。原厂资料可直接用于审查，不必先发布知识卡。知识提交回执不等于 EDA 动作回执。PCB 引脚号/焊盘号/方向单独核对，“靠近/短回路”不能擅自转成数值阈值；ERC/DRC、视觉、BOM/制造修订和实物测试分别留证，未运行写未检查。

## G. 现实演练脚本

工程师：“检查这个 MOSFET 电源模块的连接和选型依据，指出还缺什么条件。”

AI 自动定位当前模块，按需读取精确料号、封装/订货变体、符号引脚、实际网络和已有工况；关联当前对象及快照，按引用读取匹配手册的引脚图、关键正文和适用条件。不要求工程师搬运器件/网络编号或先创建知识卡，不套用近似型号资料。

工程师看到三部分：**当前工程**（实际器件、引脚和连接）；**资料内容**（对应版本的文字/图及定位）；**判断或未知**（哪些连接或选型依据可以核对，哪些条件尚缺、会影响什么）。每项判断同时绑定当前对象和资料证据，未运行的检查明确写未检查。

缺少驱动电压、负载或其他必要工况时，AI 限缩结论并列出缺项，不猜成确认值；仍可交付已能核对的连接事实和标明 unknown 的审查结果。只有缺项或冲突会改变下一步方案时才请求工程师判断。首轮审查不改图；工程师后续明确要求修改，才准备拟议影响并沿已有绘图、局部回读和最终检查链执行。

任务结束后，只在形成有依据且条件明确、值得复用的设计经验时自动整理待审核候选。未知与验证范围原样保留；无稳定经验不生成候选，沉淀失败不阻止审查交付。正式发布需要工程师审核。

必要决策最多涉及三类：改变方案的缺条件/冲突、后续高代价或超范围修改、可选正式经验发布；不是每次必需三次确认。已有确认复用，普通资料读取和已授权范围内的确定性动作不逐项询问。

## H. 可观察验收指标

沿用现有回执/审计与项目记录，不新增遥测平台。实施演练时记录：

| 指标 | 计数方式 / 成功含义 |
| --- | --- |
| 用户输入与重复确认 | 记录必要决策和可避免的重复提问，目标是未变决定不再确认 |
| 总耗时与工具往返 | 从目标到交付的实际起止、EDA/知识调用数；区分解析等待、AI 推理、执行和用户等待 |
| 返工 | 重画范围、失败后重放次数、人工指出问题数；unknown 后不盲重放 |
| 条件遗漏 | 已提供却未进入方案的关键约束数；未知不得隐去 |
| 错误落图 | 错件/错脚/错网/越范围和最终可见重叠；分类报告，不揉成单一通过率 |
| 引用可定位 | 抽查每条使用结论能否回到对应版本正文/图；保留缺失与冲突 |
| 重用收益 | 同类后续任务实际减少的读取/重复决策及耗时，与可比任务对照；无测量不写收益百分比 |

首期成功是当前一个模块的证据辅助只读审查，或用户另行授权后的局部变更闭环，且旧功能无退化：无需人搬运器件/网络编号；错料号禁止套用；未知不变成确定结论；手工相关修改让旧判断失效；每个判断定位当前对象和证据。不是“29 件在固定分钟内完成”。此轮不提供尚未测量的提速或准确率。

## 内部技术契约（保留并服务上述流程）

## 1. 目标和范围

在 kb14 现有知识服务中增加内部专题知识卡：把任务中值得复用的多份资料组织成可追溯的结论、适用条件、冲突和未知项，不作为绘图前的必填步骤。复用 Node.js 服务、SQLite、现有管理 UI、六个 knowledge MCP 工具，不增加第二个插件、服务、规则引擎或任务状态机。

资料本身、AI 的推断、工程师审核分别记录。程序确认字段和引用有效，不能证明电路结论正确；任何自动处理均不得把知识标为工程验证通过。

后续专题增强的首轮只允许创建和修改待审核候选，不修改已批准的正式知识。`baseKnowledgeRevision` 或其他正式知识更新请求明确返回 `FORMAL_UPDATE_NOT_SUPPORTED`，不得静默转成覆盖。

## 2. 已核对的现状

- `knowledge/src/service.mjs` 已有导入、检索、冻结文本读取、候选提交和本地 UI 审批。
- `knowledge/src/store.mjs` 已有 SQLite 事务、source revision 和候选 pending/approved/rejected；候选没有 revision、提交回执表。
- `knowledge/src/evidence.mjs` 已有不可变 JSON evidence snapshot、规范化 JSON 和分页读取；图片路径尚不等于冻结图片。
- `/api/asset?chunkId=` 只允许 parsed 内 PNG，但使用当前 chunk；不能作为历史证据图片的权威入口。
- `knowledge_get` 目前返回文本及结构化 JSON。通用 MCP 转换器只生成 text block；增加图片必须修改 get 专属转换。
- 当前审批把候选、source、chunks 纳入事务，但索引任务在提交后创建；文件写入和冻结证据文件也不是 SQLite 可回滚操作。

以上为源码审查结果，本设计阶段没有运行测试或更改运行状态。

## 3. 使用流程

1. 用户导入资料；等待现有 import job 报告实际解析和索引状态。
2. AI search，再用返回的 evidenceRef 读取所需完整段落；图片相关结论同时读取对应冻结图片。
3. AI 先服务当前工程方案；任务产生值得复用的内容后，自动整理专题候选：问题、结论、条件、逐条引用、冲突和未知项。页面相邻不能证明证据归属。
4. propose 创建候选。返工修改同一个 pending candidate，不生成无意义副本。
5. 用户在现有审核 UI 查看正文、证据、图片和限制，批准或拒绝。
6. 批准后发布可检索卡；索引状态单独显示。发布成功不等于向量索引成功，更不等于硬件验证成功。

有截断就继续 cursor，参数保持一致。资料缺失或矛盾不能自动补全；可以明确记录 unknown/conflict，不能将其当作确定设计依据。

## 4. 候选契约与兼容

保留现有 legacy proposal 请求和 validation 字符串兼容。新增 `kind: "topic"` 分支，其字段独立校验；不强迫专题卡伪造 problem/cause/solution。旧卡不自动生成 claims 或证据引用。

专题请求示例（标识均为示意）：

```json
{
  "kind": "topic",
  "payloadVersion": 1,
  "submissionId": "client-generated-stable-uuid",
  "expectedCandidateRevision": 0,
  "title": "接口供电条件",
  "question": "哪些条件下可采用该连接方案？",
  "domain": "schematic",
  "models": ["exact-part-number"],
  "conditions": "电压、封装、版本和工作条件",
  "notApplicable": "不适用范围",
  "claims": [
    {
      "claimId": "c1",
      "kind": "fact",
      "statement": "资料明确给出的结论",
      "evidence": [
        {"evidenceRef": "opaque-existing-reference", "unitId": "frozen-unit-id", "assetId": "optional-frozen-asset-id"}
      ]
    }
  ],
  "conflicts": [],
  "unknowns": [],
  "tags": ["interface"]
}
```

更新增加 `candidateId`，`expectedCandidateRevision` 必须等于当前候选版本。创建为 0，成功后为 1；每次有效更新加 1。`expectedCandidateRevision` 与正式知识的 revision 不混用。

- claims：1–32 条，每条稳定 claimId；每条最多 16 个引用，完整保留多对多关系。
- fact：必须引用可定位证据，不能只写路径或自由文本来源。
- calculation：另有 inputs（数值、单位、来源或明确假设）、formula、result（数值、单位）；程序检查结构，不宣布公式推导正确。
- inference：必须写 qualifications，明确推断依据和限制。
- conflicts：明确关联 claimId/证据及冲突内容；unknowns：明确尚缺什么资料。
- 复用 project/module/domain/models/tags/conditions/notApplicable 分类；不新增分类框架。
- 请求正文 UTF-8 最大 128 KiB；超限返回明确错误，不截断接收。旧请求原有限额保持兼容。

引用校验检查 snapshot 哈希、unit 归属、source 状态和可用性；不接受任意来源路径或 URL。完整读取是 AI 使用要求，引用有效不代表 AI 已读懂，服务器不伪造阅读证明。

## 5. 图片传输和冻结

`knowledge_get` 保留现有默认文本返回；新增可选 `includeVisuals` 和 `assetIds`。图片必须使用 pinned evidenceRef，且 asset 属于本次读取的冻结单元。id-only/current_unpinned 请求不能返回权威冻结图片。

复用现有解析产物。捕获新证据时，验证已登记图片的真实路径在知识根 parsed 范围内，拒绝符号链接逃逸，校验 PNG 文件头、尺寸、大小和内容哈希。合格图片复制到内容寻址的 `evidence/assets/<sha256>.png`，以冻结 manifest 绑定 source revision、source hash、unitId、asset hash；已有同哈希文件复用。不扫描文件夹、不读取任意路径、不下载 URL。

每次最多 3 张；单张最多 2 MiB，合计最多 4 MiB（解码前原始 PNG 字节），单张最多 1600 万像素。读取前检查文件大小，读取后复核哈希和尺寸；Base64 传输约增加三分之一体积。第一阶段不自动缩放或调用新图像依赖；超限返回 `too_large`，可由明确的后续任务生成登记过的预览，不能悄悄替换原证据。

旧 snapshot 没有冻结 asset hash 时返回 `unavailable_legacy`，不能拿当前图片充当历史图片。新快照可按现有资料重新捕获，但必须返回新的 evidenceRef。

输出保持原 text/structuredContent，在 get 专属 MCP 转换中追加 image content block；结构化输出顶层增加 visuals 描述（assetId、hash、source revision、unitId、status）。不把新字段塞进现有严格 context 对象，不改其他工具的结果转换。UI 使用同一受限解析器读取冻结资产。

## 6. 重复提交和并发

submissionId 由调用方生成，跨重试和会话保存，不以标题作为去重键。作用域是当前知识库 SQLite；不同库互不影响。对象键递归排序，数组顺序保持，规范化完整请求后取哈希；包括全部结论、引用、条件、冲突、操作类型和 expectedCandidateRevision。拒绝非有限数值及不合法字段，不能仅哈希 title/body。

同 submissionId + 同完整哈希：返回第一次事务存下的回执。相同 ID + 不同内容：409 `IDEMPOTENCY_CONFLICT`。真正新修改使用新的 submissionId。

事务顺序：先查回执，再校验候选版本和 pending 状态，再 create/update，最后存回执并提交。候选写入和回执必须处于同一 SQLite 事务。响应丢失后重试不会创建第二张卡；原回执返回原 revision，可附 currentRevision 区分后来修改，不能重放旧内容。

最小迁移：candidates 增加 revision（旧卡默认 1），增加提交回执表。用事务和表结构检测实现可重复的加法迁移，保留 payload/status/review，不批量重写旧卡。不宣称数据库降级自动兼容；旧程序需要停用新功能后另行评估。

## 7. 审批和发布原子边界

现有 UI 继续是唯一批准入口，MCP 不新增批准工具。UI 获取候选时取得 candidate revision 与 sourceVersionSet。版本集包含引用 sourceId/revision/hash、冻结 evidence hash，以及会影响适用性的当前条件/状态指纹；不能只看正文哈希而漏掉 metadata 变化。

审核请求绑定 `reviewSubmissionId`、`expectedCandidateRevision` 和用户看到的 sourceVersionSet。事务内再次核对；候选或来源变化返回 `REVIEW_STALE`，展示变化并要求重新审阅，不盲目重试批准。未启用或未批准来源、失效引用，以及依赖缺失图片的确定性结论阻止批准；明确 unknown/conflict 可以保留，但不能伪装已解决。

同一事务完成：候选状态、发布 source/chunks、publication 指针、审批回执、持久化索引 job。提交后再激活现有队列。启动沿用 interrupted job 行为，不自动假定索引成功。激活失败或响应丢失时，通过回执和 job 状态恢复，不再次发布。

卡文件和 evidence 文件不属于 SQLite 原子事务：先准备内容寻址/临时文件，再引用入库；失败文件可成为未引用孤儿，不能作为已发布知识被搜索。不为此增加第二套日志或状态机。发布正文保存可读 Markdown，完整 claims/引用结构保存 metadata 作为机器权威；Markdown 不是唯一数据源。

专题发布复用现有 lessons 存储与 lesson/experience 检索契约，metadata 增加 knowledgeKind=topic；语义上 UI 明确显示“专题整理”，不暗示经过硬件实验。不扩展现有 context kind/sourceType 枚举。审批后逐条、多来源引用必须完整保留。

新版 UI 审批必须携带版本；缺失时明确要求刷新，不能自动批准最新候选。旧 legacy 创建仍兼容；旧客户端不获得新请求的幂等保证。

## 8. 异常的用户与 AI 行为

| 情况 | 行为 |
| --- | --- |
| 文本截断 | 展示 partial/nextCursor，AI 续读所需范围，不宣称完整 |
| 图片缺失、过大或哈希不一致 | 展示具体状态；依赖图片的事实不能批准，改为 unknown 或补资料 |
| 引用不属于冻结单元 | 拒绝请求，指出 claimId 与引用 |
| 资料冲突 | 保留双方来源与适用条件，用户决定；不按检索分数选“真相” |
| candidate revision 过期 | 返回当前版本，AI 读取后合并；不覆盖别人修改 |
| 来源审核后变化 | REVIEW_STALE，重新审阅，不偷偷替换引用 |
| 已发布但索引失败 | 展示发布成功/索引失败，恢复索引任务，不再次发布 |
| legacy 卡无结构化证据 | 原样读取并说明来源形式，不生成虚假引用 |

## 9. 最小实施位置和顺序

本节是后续专题增强的模块依赖顺序，不替代 F 节首期工程审查顺序；store/审批/UI 增强均延期。

1. `knowledge/src/store.mjs`：候选 revision、提交/审批回执、事务 CAS、事务内创建 job。既有 source revision 不需要为此新增第二列。
2. `knowledge/src/evidence.mjs`：复用规范化与冻结逻辑，增加资产 manifest。必要时仅新增一个小资产解析模块供服务/UI 复用。
3. `knowledge/src/service.mjs`：topic 分支校验、pending update、版本绑定审批、结构化发布，沿用现有路径和队列。
4. `knowledge/src/context-contract.mjs` 与 `mcp/src/knowledge-tools.mjs`：同步可选字段和 get 专属图片输出；六个工具名称保持不变。
5. `knowledge/ui/app.js`：候选逐条证据、图片、冲突、未知项和 stale 提示；不重做 Dashboard。

每一步沿实际依赖推进，不提前接入 EDA 或修改正式库。旧 lesson 字段继续复用原渲染分支。

## 10. 实施后的验收计划（本轮不运行）

使用临时独立知识根与现有 Node 测试方式，不接触个人正式库：

- legacy 字符串 validation、旧卡读取与六工具默认返回兼容。
- 同 key 同完整内容只写一次；键顺序变化仍相同；证据/条件变化必冲突；响应丢失可取回原结果。
- 两个更新竞争只允许匹配 revision 的一个成功；回执写失败时候选不留下半次更新。
- 多 claims、多来源、多图片引用批准后无损；正式卡更新明确拒绝。
- source 正文、条件或状态改变后审批 stale；不能批准用户未看到的版本。
- 图片范围、链接逃逸、PNG 类型、字节/像素限制、哈希、旧 snapshot 和 MCP image block 均有覆盖。
- 发布事务失败无可搜索半成品；发布成功但队列启动失败仍可追溯且不重复发布。
- 用户实际完成一次导入→读取→候选返工→审核→检索回读，分别记录解析、发布、索引结果。

离线测试通过只能证明实现边界；正式运行验收另需用户授权，不能宣称硬件正确。

## 11. AICO 借鉴与非目标

借鉴 AICO 的原始资料与派生分析分离、图文联合读取、人工整理和版本追溯。协调方提供的静态审查提醒本设计避免：JSON 键顺序影响哈希、仅标题正文去重、提交后准备失败被误认为未提交、发布时丢失多证据引用。它们是参考风险，不宣称是 kb14 已复现缺陷。

参考固定版本：AICO-knowledge README `079bd4cbd90e6e1ac8a266520e60e54108b7e75d`；AICO Wiki `31ddddec2d0efce031799667de3246f8af3680de`。当前仅借鉴设计，不复制未审许可证代码。

本阶段不做：聊天 UI、自动批准、自动设计电路、知识自动升级成程序规则、全库批量重建、正式知识覆盖、来源更新自动改工程、外部平台同步、额外 RAG/LLM 依赖和完整阅读状态机。

假设：同一个知识根共用一个 SQLite 和现有写队列；用户审核仍是正式知识发布条件。没有参考原理图或完整资料时明确写 unknown，不依靠模型补成“已验证知识”。
