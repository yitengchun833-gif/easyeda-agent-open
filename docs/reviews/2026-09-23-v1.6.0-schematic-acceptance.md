验证本地 `1.6.0-dev.1` 首轮及后续 `dev.3`–`dev.7` 修正候选在 Web EasyEDA Pro 中能从原始需求生成完整原理图，

和旧工程的历史通过记录均不计入本轮结论。操作和判据以
[数据驱动架构基准](../../.agents/skills/easyeda-agent/references/schematic-data.md#数据驱动架构基准)、
[执行流程](../../.agents/skills/easyeda-agent/references/auto-layout-sop.md)及
[现行验收标准](../e2e-automation-acceptance.md)为准。

测试工程按用户要求新建为 `easyeda-v160-schematic-test-20260923`，不改动既有 `ceshi`。
输入只给
[`esp32MiniRequire.md`「一、客户原始需求」](../../esp32MiniRequire.md#一客户原始需求)；
不给 BOM、UUID、网表、器件坐标、预制源 JSON 或答案图。测试前确认工程/文档在
`easyeda health.windows` 中精确出现，并记录 CLI、daemon、Skill、connector 与宿主版本。
同一窗口所有 typed 调用串行执行。

## 证据与判定

每轮在仓库外或忽略目录保留：原始需求、未改写的官方快照、目标源、测量来源、算法参数
和提交号、SHA-256、完整候选/选中页、固定导图、队列 dry-run、执行 journal、fresh
`sch list`/`connectivity`/`read`、逐页 `layout-lint`/`check`/`bridge-check`/DRC/strict gate、
实例身份与 `uniqueId`/属性、范围外差分，以及 save/reload 后第二份 fresh 回读。
每轮冻结自己的版本、输入哈希和证据清单；逐条客户需求须标 `pass`、`fail` 或未能由
原理图证明。对象比对未覆盖图形时，不得用引脚连接一致代替完整原理图对账。
验收报告按场景记录 `pass`、`fail`、`blocked` 或 `not-run`，并给出证据路径和第一条失败对象。
缺测、连接器未加载、宿主持续加载、保存/重载失败一律不能记 `pass`。
