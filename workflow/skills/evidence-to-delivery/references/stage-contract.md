# 阶段任务契约

默认在当前任务依次完成“资料分析与方案制定”“原理图执行与验收”，复用同一项目目录和状态。只有用户明确要求拆分任务时才启用下述创建、等待及回传条款；逻辑阶段不等于必须创建新对话。共享目录一次只有一个写入者。

数据写入遵循 [结构化状态契约](structured-workflow.md)：findings.md 保存证据；workflow.py 维护唯一 state.json 并生成 task_plan.md/progress.md，不手工维护第二套状态。

所有阶段先遵守 [全流程共用规则](../SKILL.md#全流程共用规则)；规则冲突、用户暂停及局部验证范围随交接传递，不因切换任务丢失。

硬件任务的规则归属、约束交接、布局/布线与验收边界统一见 [硬件交付衔接](hardware-delivery.md)。具体专业门槛按当前适用Skill，执行与恢复遵循[统一运行契约](structured-workflow.md#统一运行契约)，不在阶段契约重复定义或固定某次开发任务的范围。

## 创建与接续

- 使用新的顶层 Codex 任务，不用 fork 或子代理冒充独立任务。使用用户授权的同一已保存项目目录，不创建隔离工作树。
- 提示包含用户目标、项目绝对路径、阶段与检查点、协调任务 ID、授权来源、输入输出、实际可读 Skill 路径、职责及出口。阶段任务不得递归创建任务。
- 阶段一读取本 Skill、本契约、同级 document-intake/SKILL.md，图表按需使用 pdf-intake/spreadsheet-intake，需要外部证据时使用 information-collection-orchestrator。阶段二按交付物使用专业 Skill。先验证实际路径可读，再传入任务。
- 创建前核对已登记任务 ID 与实际状态；有对应任务就接续。返回不确定先查证，客户端 ID 不当正式任务 ID。
- 新任务首条只读确认就绪；协调任务取得正式 ID 并登记后立即发送开始，再等待完成或待答。创建成功不等于工作已启动。
- 资料分批追加给同一个阶段一任务；从检查点 A 转 B 不创建新对话，不要求用户说“下一步”。新资料只补查受影响结论。
- 阶段任务将待答问题、方案、预览和交付证据返回总控，不要求用户切换任务；总控通过任务工具收取和回传，不要求用户复制摘要。总控转述问题时包含证据、影响和建议；把用户答案原样回传，阶段任务记录来源并确认接收。用户直接在阶段任务回答时复用落盘答案，不重复询问。
- 已授权范围内接续无需重复确认。阶段创建授权不代替具体方案批准或目标系统操作授权。

## 阶段一：资料分析与方案制定

同一对话按两个检查点推进，可因补充资料在内部回查，但证据事实和工程选择分别记录。

### 检查点 A：资料核对

- 登记全部资料的位置、版本、对象、解析状态与分析覆盖；原件只读。记录成功、部分成功、失败，不把解析成功当成内容已核对。
- 核对当前目标需要的原文与关键图表，结论附页码/章节/图表定位；解析错误按清楚的原文纠正。
- 资料自身含糊、冲突或缺定义时列出证据、影响与建议。不能以助手推测或用户偏好补造厂家事实。
- 项目目标和范围仅澄清到足以指导阅读；已知范围、设备和已答问题复用真实记录。
- 测点数量、测试电压选择、通道覆盖、夹具配置等工程选择留给检查点 B；不得把这些尚未设计的内容视为“资料未读懂”。
- 出口：按下方“资料理解校对与确认”展示完整核对摘要，用户已明确确认所用版本和范围，或明确更正/排除有问题的部分；关键事实、矛盾和缺口可追溯。未确认前可继续独立分析及准备标明未确认的候选方案，不能把它们作为已确认执行依据。允许带着明确未决问题进入 B 的草案讨论；依赖未决事实的部分不得批准执行。

### 资料理解校对与确认（形成执行规则的前提）

资料摘要、执行方案和适用规则可合并为一次简短审阅，真实用户回复分别绑定相应版本和范围；不因分成A/B两个逻辑检查点强制增加确认轮次。已明确给出的设计、画法要求和执行授权直接作为依据，只有未决定的设计选择或范围变化才追加询问。程序校验绑定和证据，不能替代实际理解原文。

1. **接收与登记。** 汇总附件/原件及后续补充，记录来源、有效版本、适用型号/对象、替代关系和接收范围。支持分批投喂，不以一次上传或用户沉默推定资料齐全；缺文件、打不开、解析失败分别列出。
2. **解析并核原件。** 依据目标提取信息，分别记录解析、核对和分析覆盖；关键脚号、极性、单位、数值、脚注、连接点/交叉及图面关系回原件核对。原件不改写，解析成功不等于理解正确。清楚的提取错误自行按原文纠正并告知，原文缺失/矛盾不猜补。
3. **输出完整资料核对摘要。** 使用简洁表格列出资料/版本与出处、提取事实或要求、原文核对状态、疑问及影响。硬件任务至少覆盖本次所需器件/参数/脚号、网络关系、布局表达、操作范围及验收目标。区分原件事实、用户要求、助手建议与仅作参考的视觉特征；不能只展示疑问而不展示已理解内容，也不要求用户重读整份资料。
4. **用户校对与更正。** 展示摘要请用户确认理解和任务适用范围。用户纠正后回查来源，更新摘要并指出变化；必要时重新提交修订后完整摘要。用户的设计变更单独记为用户要求，不反写成厂商事实；未知结论不会因用户认可就成为技术已验证。
5. **确认基线。** 保存真实确认原话/位置、摘要版本、对应资料版本/指纹、确认范围及保留缺口，复用既有来源/决定记录。只有确认范围内且已核对的事实才能作为确定执行依据；暂定事项保留暂定属性，关键缺口须补查或缩小范围。资料确认不等于允许开始画图；沉默、上传、解析成功及助手自己说“已确认”均不算用户确认。
6. **交给规则整理。** 从确认基线提取外部要求，与内部通用规范合并，输出完整带版本的执行规则和检查方法，再取得规则确认。每条外部规则可追到基线条目/用户要求；已有同版本同范围真实确认可复用，不要求机械重复。一条回复可分别明确确认资料和规则，但两份内容必须均已展示且版本清楚。
7. **变更回路。** 新资料、纠正或规则讨论暴露事实缺口时，检查影响到的资料结论、规则和执行结果。更新当前摘要、展示变化并复核/确认受影响范围，未变范围沿用真实确认。执行规则变化更新完整本地清单，向用户说明变化和影响并确认受影响范围；相关旧检查标为待重核，不能改版本号冒充新证据。

最少交接内容为“确认后的资料摘要及版本/范围 → 本次执行规则及版本 → 真实用户确认位置 → 检查结果”。复用 findings.md 和现有 source/decision/propose/approve/result/context，不建立第二套确认状态机。当前脚本只校验部分字段、指纹和依赖，不能自动证明原文理解正确或用户确认真实；必须核对实际记录。

### 检查点 B：方案制定与确认

- 同一任务结合检查点 A 结论核对实际设备、接口、版本、夹具、优先级、限制与验收要求，给出具体建议及依据，只问会改变结果的缺失条件。
- 区分必须解决项、建议默认值、暂不影响当前范围的事项。工程选择不能伪装成手册规定；默认值随方案取得认可，不能自动批准。
- 新需求产生证据缺口时在本任务定向回查 A，更新 findings.md 和关联来源，再继续方案；不在两个任务间反复派发。
- 用 propose 记录固定编号方案项、依据、依赖、共用对象、步骤、停止条件和验收标准。用户明确确认当前修订后才 approve；checkpoint 按结构化契约保存方案历史。
- 影响执行的事实缺口必须查明，或经用户确认缩小范围/暂缓对应项目。用户也不清楚时给出补查建议，不强迫猜测。
- 阶段一出口：A 的资料理解校对及确认记录可用，B 的必要问题已处理；当前方案修订已获真实确认，批准范围内无未解决阻断，暂缓项目及恢复条件可查。资料确认、方案/执行规则确认及成果验收分开记录，不互相代替。
- 原理图方案一并记录电路、用户画法偏好和绘图授权。用户已要求按该方案绘制时，既定规则下的位置、方向与短线表达由助手执行；新增设计选择或超出授权范围才返回确认。

### 阶段一提示模板

> 你是阶段一“资料分析与方案制定”。先读取项目规则、阶段契约和当前记录。原件只读，先完成检查点 A 的解析与证据核对，再在同一对话完成检查点 B 的需求澄清、设备可行性和方案制定。标明手册事实、工程建议、用户决定与未决问题；复用已回答内容，不要求用户替你设计。分析写 findings.md，方案及确认按结构化契约记录。把具体方案、疑问及建议提交总控，由总控与用户确认；不得操作目标系统，不创建下游任务。

## 阶段二：专业执行与验收

- 先整合内部规范、用户及已确认资料，展示完整带版本的本任务执行清单：具体要求、来源、适用条件、检查方法、冲突和未确认项，以及必要预览。用户补充或修改后更新同一份完整本地清单，面向用户简述变化、影响和需决定事项；不反复搬运未变内容。
- 首次绘图及规则变化后取得当前版本的真实明确确认，记录确认来源、版本/指纹及范围后才写入。补充规则不等于确认合并清单，旧版本不授权新版本；同版同范围有效确认不重复请求。暂停/终止后还须明确恢复授权，规则确认不自动取消停止指令。未确认只读和离线准备，不能借预览写EDA。
- 阶段一出口通过且当前方案和绘图授权明确后，在当前任务进入执行；只有已授权拆分时才创建或接续阶段二任务。
- 阶段二先连接目标并读取必要器件、引脚与网络，再按已确认方案执行；需要用户选择的画法才展示必要预览。复用同一来源、方案和规则绑定，已有绘图授权不再因进入新阶段重复确认。改变电路或出现关键事实缺口时回到相关资料和方案项。
- 执行任务读取已批准方案和必要证据，使用对应专业 Skill，作为目标系统唯一写入者。每批读回，视觉任务查看真实渲染，检查、保存和用户验收分别报告。
- 遇到新歧义或范围变化，暂停受影响执行并交总控接续阶段一；两任务不能并行写入。阶段一补查和修订后，受影响方案重新确认，再恢复原执行任务。
- 出口：真实交付物存在，关键属性/连接已读回，必要检查与视觉验收有证据，警告已解释或明确阻断，保存与用户验收状态分别记录。

### 阶段二提示模板

> 你是阶段二“专业执行与验收”。读取项目规则、已确认 task_plan.md 和必要 findings.md，按对应专业 Skill 执行。先完成连接及必要只读准备，复用有效方案和绘图授权；未决定的设计选择再提交确认。你是唯一写入者；每个副作用批次读回，按计划检查并保存，使用 result 记录实际结果与证据。遇到影响范围或正确性的新情况暂停受影响部分，向总控提交问题；未经确认不改变方案，不创建任务。

## 恢复、记录与旧项目兼容

- 阶段一 context.stage 使用 analysis 或 planning 表示内部检查点，阶段二使用 execution；tasks 使用真实职责键 analysis_plan、execution 保存正式 ID。这些是现有 context 的值，不新增状态机。
- 新任务先 check/next；view_issues非空或recovery_blocked为true时暂停接续，核对差异并按结构化契约修复，再按相关索引读 findings、方案及执行记录。关键确认要核对正文，不能凭摘要或“已完成”一句话宣布出口通过。
- 正在运行则等待；中断先核对已落盘结果和现场，再接续，避免重做。额度或工具不可用时报告具体阻碍，不承诺应用关闭或协调任务停止后自行唤醒。
- 旧三阶段项目保留全部任务 ID、证据和确认历史。只有原资料分析任务时，复用它承担合并阶段；若已有需求方案任务，选择它作为合并阶段的唯一负责人，原分析任务作为证据来源。已有执行任务继续承担执行职责，不为改名重复创建任务。
- 采用新安排时明确映射原任务职责，逐一通知需要继续的任务读取新版规则；未通知的旧会话不宣称已更新。已有授权覆盖范围内可复用，原方案确认只对未变范围有效。
- 旧手工 Markdown 状态按结构化契约明确迁移，不直接 init 覆盖；本规则更新本身不迁移任何业务项目。
- 总控在阶段任务暂停或完成后才更新派发状态；同一时间一个记录者。状态与现场冲突，以实际读回为准。
